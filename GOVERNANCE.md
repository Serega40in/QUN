# Управление разработкой QUN

Статус документа: начальная рабочая модель управления, подлежащая развитию вместе с сообществом.

## Принципы

- **Открытость:** предложения, обсуждения и решения по возможности доступны публично.
- **Ответственность:** у каждого компонента есть сопровождающий, отвечающий за качество и совместимость.
- **Безопасность прежде скорости:** критические изменения требуют более строгой проверки.
- **Независимость:** разработчики могут создавать отдельные продукты на базе публично документированных интерфейсов и применимых лицензий.
- **Проверяемость:** решения и релизы должны быть связаны с кодом, тестами и историей изменений.

## Роли

- **Contributor:** предлагает изменения через Issues и Pull Requests.
- **Reviewer:** проверяет код, тесты, архитектуру и последствия изменений.
- **Maintainer:** отвечает за компонент, может запрашивать изменения и одобрять PR в пределах предоставленных прав.
- **Project Lead:** определяет общие приоритеты проекта и назначает ответственных за критические направления.

Роль в документации сама по себе не предоставляет технических прав GitHub. Доступ выдаётся отдельно по принципу минимально необходимых полномочий.

## Как принимаются изменения

1. Для небольших локальных исправлений достаточно Pull Request с объяснением и подходящими проверками.
2. Для новых функций, изменений API и схем данных сначала создаётся Issue с предложением и обсуждением обратной совместимости.
3. Для криптографии, авторизации, кошелька, сетевых протоколов, хранения данных и выполнения задач на узлах требуются профильное ревью и дополнительные тесты.
4. Сопровождающий, не являющийся автором PR, принимает решение после рассмотрения замечаний и статуса CI.
5. При существенном несогласии решение и аргументы фиксируются в Issue или отдельной записи архитектурного решения.

Автоматический CI не заменяет ревью. Автор PR не должен одобрять собственное изменение. Ветка `main` должна быть защищена настройками GitHub до публичного масштабирования вклада сообщества.

## Выпуск и инциденты

Релизы должны ссылаться на проверенный коммит и содержать описание изменений и известных ограничений. При регрессии сопровождающие могут остановить распространение релиза, выпустить исправление или выполнить откат. Инциденты безопасности обрабатываются по [SECURITY.md](SECURITY.md).

## Лицензии и использование бренда

Лицензия исходного кода, лицензии отдельных модулей, документации и правила использования товарных знаков QUN — разные вопросы. До официального утверждения лицензии не следует обещать права, которые ещё не предоставлены. Изменения лицензирования требуют отдельного публичного обсуждения и юридической проверки.

## Эволюция управления

Эта модель минимальна и не создаёт юридического лица, токеновых прав, долей собственности или гарантированного вознаграждения. По мере появления независимых сопровождающих и внешних участников правила следует пересмотреть публично.
