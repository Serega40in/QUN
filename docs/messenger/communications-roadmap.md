# QUN Messenger — дорожная карта коммуникаций

Статус: проектирование, версия 0.1  
Дата: 2026-10-13

## Цель

Развить текущий MVP QUN Messenger (веб + Android, Supabase Auth/PostgreSQL/RLS) в единое приложение для личного общения, звонков, медиа и сообществ. Разработка должна сохранять работающие вход, переписку и доставку обновлений; новые возможности выпускать небольшими проверяемыми этапами.

Это целевая дорожная карта, а не утверждение, что перечисленные функции уже реализованы.

## Продуктовые модули

1. **QUN Chat** — личные диалоги, группы, ответы, реакции, пересылка, редактирование/удаление, поиск, закрепление, статусы доставки и непрочитанные сообщения.
2. **QUN Calls** — интернет-аудиозвонки и видеозвонки 1:1, входящий вызов, уведомления, история, переключение камеры, mute, громкая связь.
3. **QUN Media** — голосовые сообщения, фото/видео/файлы, стикеры и наборы, короткие круглые видеосообщения («видеокружочки»), избранное и предпросмотр.
4. **QUN Communities** — группы и супергруппы, публичные/приватные каналы, роли администраторов, приглашения, модерация.
5. **QUN Stories** — публикации фото/видео с ограниченным сроком жизни, аудитория и приватность, просмотры и реакции.
6. **QUN Network** — поэтапный перенос API и хранения на собственные узлы с резервированием и восстановлением. Децентрализация — отдельная инфраструктурная программа; не блокирует разработку функций клиента.

## Предлагаемый порядок работ

### M0 — стабилизация основы
- Проверить два независимых аккаунта на web и Android.
- Проверить вход/выход, повторный вход, RLS для профилей, диалогов и сообщений.
- Устранить ошибки синхронизации списка диалогов, непрочитанных сообщений и уведомлений.
- Добавить регрессионный чек-лист и тестовые сценарии; не менять auth/RLS без тестов.

**Критерий выхода:** два пользователя стабильно обмениваются сообщениями; чужие приватные диалоги и профили недоступны.

### M1 — медиа и голосовые сообщения
- Согласовать ограничения размера, MIME-типы, длительность и квоты.
- Загружать медиа через приватное хранилище с проверкой доступа и краткоживущими URL.
- Сохранить метаданные вложений отдельно от сообщений; показывать прогресс, ошибки и повторную отправку.
- Записать/воспроизвести голосовое сообщение; добавить стикеры как тип сообщения.
- Круглые видеосообщения реализовать как короткие видеофайлы с превью и ограничением длительности, а не как отдельный транспорт.

**Критерий выхода:** загрузка и воспроизведение проверены на медленной сети и при повторной отправке; приватные файлы нельзя получить без авторизации.

### M2 — аудио- и видеозвонки 1:1
- Использовать WebRTC для медиапотока; отдельный сигнальный канал для offer/answer, ICE-кандидатов, статуса вызова и завершения.
- Для прохождения NAT настроить STUN и управляемый TURN; предусмотреть лимиты, аутентификацию и мониторинг TURN.
- Реализовать состояния: ringing, accepted, rejected, missed, ended, failed.
- Для Android предусмотреть разрешения камеры/микрофона, обработку сворачивания приложения и входящего вызова; для web — запрос разрешений и управление устройствами.
- Уведомления о входящем вызове не считать гарантированными, пока не реализован и не проверен push-механизм на целевых ОС.

**Критерий выхода:** успешный звонок между разными сетями (например, Wi-Fi и мобильный интернет), завершение/отказ, восстановление после потери сети и проверка качества.

### M3 — группы и каналы
- Разделить модели личного диалога, группы и каналов; определить права участников и администраторов.
- Для каналов ввести подписки, публикации, реакции и настройки приватности.
- Для групповых звонков использовать SFU, а не пытаться ретранслировать все медиапотоки через обычный API-сервер.
- Групповые звонки и демонстрацию экрана выпускать после стабильных звонков 1:1.

### M4 — сторис
- Модель публикации, время окончания, аудитория, просмотры и реакции.
- Очистка истёкших объектов и связанных медиа по политике хранения.
- Приватность и модерация должны быть частью первой реализации, а не поздним дополнением.

### M5 — инфраструктура QUN Network
- Сначала вынести статику/медиа и отдельные сервисы, затем тестировать миграцию API и базы.
- Ввести резервные копии, проверяемое восстановление, контроль целостности, мониторинг и план отката.
- Начать с нескольких независимых узлов и явно описанного режима отказа.
- Не переносить единственную production-базу на экспериментальные узлы до тестов восстановления и согласованности.
- Разделять доступность сервиса и децентрализацию: наличие нескольких серверов у одного провайдера не равно независимой сети.

## Архитектурные границы

- **Клиенты:** web и Android; общие контракты API и единая модель сообщений.
- **Auth и данные:** текущие Supabase Auth/PostgreSQL/RLS остаются исходной точкой до отдельного решения о миграции.
- **Realtime/signaling:** сообщения и сигнальные события звонка должны быть логически разделены.
- **Медиа:** отдельное хранилище объектов, проверка авторизации, квоты и политика удаления.
- **Звонки:** WebRTC + STUN/TURN; SFU для групповых звонков.
- **Push:** отдельная подсистема для Android и web, с явным управлением разрешениями.
- **Наблюдаемость:** обезличенные технические метрики и логи; не писать содержимое личных сообщений, токены или ключи в логи.

## Безопасность и приватность — обязательные требования

- Проверить каждую таблицу и Storage policy на доступ по принципу наименьших привилегий.
- Секретные серверные ключи не включать в web bundle, APK, репозиторий или логи.
- Ограничивать размер/тип/частоту загрузок; защищаться от спама и перебора.
- Продумать сквозное шифрование отдельно: WebRTC само по себе не обеспечивает сквозное шифрование всей архитектуры звонка и хранения; серверная сигнализация не должна раскрывать ключевой материал.
- Определить управление ключами, восстановление доступа, блокировку пользователей, жалобы и удаление данных до публичного запуска.
- Не заявлять «полное E2E-шифрование» до независимого тестирования протокола и реализации.

## Тестирование и выпуск

Для каждого этапа:
1. Изменения в отдельной ветке и code review.
2. Проверки web build и Android build.
3. Тесты авторизации/RLS и сценарии двух пользователей.
4. Тест на плохую сеть, повторные запросы и частичный отказ.
5. Релиз-кандидат, проверка на реальных устройствах и возможность отката.

## Что требуется перед началом реализации

Актуальный код проекта, сведения о текущих таблицах/политиках Supabase и способах развёртывания. Старый архив Telegram-чата не является исходным кодом и не должен использоваться как источник истины о текущей реализации.

## Рекомендуемый следующий шаг

Начать с M0: аудит актуального репозитория и проверка текущих потоков авторизации, сообщений и уведомлений. Затем реализовать M1 (медиа/голосовые) и M2 (звонки 1:1) параллельно только там, где контракты и тесты уже определены.
