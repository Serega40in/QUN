# QUN Finance MVP v1 — аудит исходного состояния

Дата аудита: 2026-11-24  
Область: GitHub `Serega40in/QUN`, связанный Supabase-проект QUN.

## Что уже есть

- Публичный интерфейс: `docs/qun-wallet/index.html`, GitHub Pages `/qun-wallet/`.
- Общая авторизация QUN ID через существующий Supabase Auth и `../assets/qun-auth.js`.
- Supabase project ref: `qdxjltqlnphvzafapncm`, регион `eu-central-1`, статус при аудите `ACTIVE_HEALTHY`.
- Таблицы `public.qun_wallets` и `public.qun_wallet_transactions`.
- RPC: `qun_wallet_get_or_create()`, `qun_wallet_claim_test_tokens()`, `qun_wallet_transfer(text,numeric,uuid,text)`.
- RLS включён; прямые INSERT/UPDATE балансов клиентским ролям запрещены в опубликованном schema snapshot.
- Перевод выполняется серверной SQL-функцией; есть проверка владельца, достаточного баланса, точности, адреса, собственного адреса, memo и request_id.
- Есть уникальный индекс для повторного request_id отправителя и индекс для разовой тестовой выдачи.

## Критические границы

- Текущий QUN — внутренние тестовые единицы в PostgreSQL. Это не блокчейн, не токен mainnet, не депозит и не деньги с денежной стоимостью.
- Текущий ledger хранит изменяемый агрегированный balance и запись о переводе, но не полноценные сбалансированные double-entry проводки.
- Публичный адрес имеет формат внутреннего идентификатора `QUN...`, а не криптографический on-chain адрес.
- Криптографические ключи и seed phrase не создаются; self-custody TON wallet не реализован.
- Нет подтверждённой интеграции с банковским/платёжным провайдером.
- Документация не доказывает фактическую корректность всех сценариев; требуются тесты двух отдельных пользователей, конкурентных переводов, повторных запросов и RLS.

## Найденный дефект интерфейса

В `docs/qun-wallet/index.html` состояние одноразового faucet определяется запросом к таблице всех транзакций типа `test_faucet` без фильтра текущего кошелька. После выдачи тестовых QUN одному пользователю интерфейс может показывать кнопку как уже использованную у другого пользователя. RPC-функция проверяет конкретный кошелёк; интерфейсный запрос должен также фильтровать по `recipient_wallet_id = wallet.id`.

## Supabase Advisor — наблюдения на момент аудита

- Предупреждение `auth_leaked_password_protection`: защита от скомпрометированных паролей выключена.
- `SECURITY DEFINER` RPC доступны authenticated роли, включая три wallet RPC. Для этих функций это может быть намеренно; необходимо проверить тело, search_path, grants и тесты авторизации, а не просто отключать доступ.
- Есть другие таблицы с RLS enabled/no policy. Это отдельная зона экосистемы QUN, не менять её в рамках кошелька без аудита владельцев и сценариев.
- Есть рекомендации по индексам внешних ключей в других таблицах.

## Безопасный план

1. Работать в ветке `feature/qun-finance-mvp-v1`; не выполнять разрушительные изменения существующих таблиц.
2. Исправить UI-ошибку faucet.
3. Подготовить additive migration для двойного журнала, не переключая существующий баланс без сверки и тестов.
4. Добавить автоматизированные тесты бизнес-инвариантов и инструкцию локального запуска.
5. Проверить существующий интерфейс и backend на двух тестовых аккаунтах.
6. Отдельно исследовать TON Connect/self-custody, не генерировать и не хранить seed phrase на сервере.
7. До реальных денег — юридическая оценка целевых стран, провайдеров, защиты данных, AML/KYC и информационной безопасности.

## Что не утверждается

Этот аудит не является независимым penetration test, юридическим заключением или доказательством production readiness. Реальные платежи, mainnet, выпуск карт и custody не подтверждены.
