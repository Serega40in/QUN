# QUN Finance MVP v1 — архитектура

## Принципы

- Сначала тестовый продукт; никаких клиентских фиатных средств в нашем внутреннем ledger.
- QUN ID остаётся общей идентичностью, финансовые таблицы и RPC получают отдельные минимальные grants.
- Фиат, тестовые единицы QUN и on-chain активы — три разных домена данных.
- Не хранить приватные ключи, seed phrases, банковские реквизиты карт или секреты провайдеров в браузере/репозитории.
- Все денежные значения — integer в минимальных единицах либо PostgreSQL NUMERIC с явно заданной точностью; никаких float для бухгалтерского учёта.
- История проводок append-only; исправления — компенсирующими проводками, не UPDATE/DELETE.
- Каждая команда изменения состояния имеет idempotency key, серверную проверку пользователя, атомарную транзакцию и audit metadata.
- Никакие реальные платежи не активируются до договора с регулируемым провайдером и юридического одобрения.

## Компоненты v1

1. React/TypeScript PWA — позже, если нужен новый клиент. Текущий HTML клиент сохраняем до завершения миграции.
2. QUN ID / Supabase Auth — аутентификация. Не доверять username из клиента как идентификатору; использовать verified auth.uid().
3. PostgreSQL — текущие тестовые кошельки и отдельный append-only journal.
4. RPC — все изменения состояния только на серверной стороне.
5. TON Connect — отдельная интеграция, которая просит пользователя подключить внешний кошелёк и подписывать транзакции. Сервер не получает seed phrase.
6. Bank/payment adapter — будущий изолированный адаптер к провайдеру; выключен по умолчанию.
7. Audit/monitoring — технические события без секретов, rate limiting и алерты.

## Домены данных

- `test_ledger`: тестовые единицы QUN, без денежной стоимости.
- `crypto_wallet_connections`: публичный адрес, сеть, статус подключения и timestamps; никогда не private key/seed.
- `provider_accounts`: opaque provider customer/account IDs, только после партнёрской интеграции.
- `provider_events`: подписанные/проверенные события провайдера с дедупликацией.
- `double_entry_journal`: append-only проводки, каждая операция сбалансирована по активу.
- `audit_events`: административные и чувствительные события с минимизацией персональных данных.

## Этапы

- A: исправить существующий MVP и тесты.
- B: добавить double-entry journal рядом с текущей схемой, заполнить тестовыми/сверенными событиями и проверить равенство сумм.
- C: перейти на чтение баланса из ledger только после reconciliation и доказанных инвариантов.
- D: TON Connect в testnet с тестовыми активами и без custody.
- E: выбрать одну стартовую юрисдикцию и провайдера; интеграция только после правовой и security review.
- F: production readiness — внешний аудит, мониторинг, резервное восстановление, инцидентный план и договоры.

## Инварианты

- Сумма дебета и кредита по каждой операции равна нулю в пределах одного актива.
- Баланс не может стать отрицательным.
- Повторный idempotency key не создаёт вторую операцию.
- Пользователь может читать только собственные записи и явно доступные публичные данные.
- Адрес получателя и сеть проверяются на сервере перед отправкой on-chain.
- Статус on-chain операции определяется подтверждениями сети, а не только ответом браузера.
