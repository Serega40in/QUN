# QUNHub — концепция и дорожная карта

## Видение

**QUNHub — независимая платформа совместной разработки и публикации проектов экосистемы QUN.** Она должна сделать разработку открытой и удобной: от первого Issue и форка до ревью, релиза, документации и каталога приложений.

QUNHub не следует выдавать за уже реализованную замену GitHub. Текущий Developer Hub — первая страница входа поверх GitHub Pages. Полноценный QUNHub потребует самостоятельного продукта, безопасной архитектуры и поэтапной миграции без потери Git-совместимости.

## Основные пользовательские сценарии

1. **Разработчик ядра:** находит задачу, форкает репозиторий, создаёт ветку, открывает PR, проходит CI и ревью.
2. **Создатель независимого продукта:** публикует репозиторий, документацию, лицензию, релизы и сведения о совместимости с QUN.
3. **Команда:** управляет организациями, командами, ролями, Issues, проектами и релизами.
4. **Пользователь экосистемы:** ищет библиотеки, приложения, ботов, SDK и сервисы; проверяет источник, версию, лицензию и статус поддержки.
5. **Сопровождающий:** управляет ревью, CI, релизами, безопасностью и доступом без единоличного скрытого контроля над пользовательскими проектами.

## Принципы архитектуры

- Git остаётся переносимым: clone/fetch/push через стандартные Git-протоколы, импорт и экспорт репозиториев.
- Сначала используем существующий GitHub как upstream и CI, а QUNHub строим отдельно; не дублируем критичные функции раньше времени.
- Публичные проекты могут иметь собственных владельцев и лицензии. Включение в каталог QUN не передаёт проект в собственность QUN.
- Идентификация, авторизация и права доступа проверяются на сервере. Никакие секреты и доверие нельзя основывать только на интерфейсе браузера.
- Действия, требующие доверия, журналируются; опасные действия защищаются минимальными правами, подтверждениями и аудитом.
- Не исполнять произвольный код участников в production-окружении. CI должен быть изолирован, с ограниченными правами и без production-секретов.
- Не создавать собственный блокчейн или токен только ради хранения метаданных репозиториев. Первые версии не требуют токена.

## Поэтапная дорожная карта

### Этап 0 — Contributor Workflow (текущий)

- CONTRIBUTING, GOVERNANCE, SECURITY и Code of Conduct.
- Шаблоны Issues и Pull Request.
- Базовые проверки входящих PR.
- Публичный Developer Hub и понятный первый вклад.
- Проверка текущих workflow перед включением защиты `main`.

**Критерий завершения:** новый участник может пройти путь от инструкции до PR; изменения не получают production-секреты автоматически.

### Этап 1 — QUN Developer Portal

- Каталог официальных API, SDK, документации и примеров.
- Реестр компонентов: владелец, репозиторий, лицензия, поддерживаемые версии, статус и тесты.
- Каталог независимых проектов с добровольной регистрацией.
- Поиск по проектам и фильтры по языку, типу, лицензии и совместимости.
- Публичная дорожная карта и задачи для сообщества.

### Этап 2 — QUNHub MVP поверх GitHub

- Вход через GitHub OAuth с минимальными разрешениями.
- Список проектов и карточки репозиториев, Issues, PR и CI-статусы через официальные API.
- Каталог продуктов и SDK с ссылками на исходники и релизы.
- Не хранить GitHub access tokens в клиентском коде; OAuth-секреты и токены — только на сервере.
- В MVP Git-операции и ревью остаются в GitHub, пока собственная forge-инфраструктура не будет готова.

### Этап 3 — собственная Git-платформа

Перед выбором реализации сравнить поддерживаемые self-hosted forge-решения и стоимость эксплуатации. Не писать Git-хостинг с нуля без доказанной потребности.

- Git-репозитории, организации, команды, права доступа и webhooks.
- Issues, pull/merge requests, review, protected branches и releases.
- Изолированные CI runners, секреты, журнал аудита и защита от злоупотреблений.
- Резервное копирование, восстановление, мониторинг и план реагирования на инциденты.
- Импорт/экспорт GitHub и других Git-хостингов.

### Этап 4 — экосистема и федерация

- Подписанные метаданные релизов и проверяемое происхождение сборок.
- Версионирование SDK и правила совместимости.
- Федеративные каталоги независимых экземпляров QUNHub, если это будет востребовано.
- Децентрализованное хранение — только как дополнительный слой с проверкой целостности, доступности и прав; не единственное место хранения критичного исходного кода.

## Критерии успеха

- Репозитории и история Git экспортируются без привязки к QUNHub.
- Можно проверить владельца проекта, лицензию, исходный код и происхождение релиза.
- Пользовательские проекты не получают неявного доступа к секретам или инфраструктуре.
- Участник может внести вклад без разрешения на запись в основную ветку.
- Платформа выдерживает восстановление из резервной копии и имеет понятный путь обработки инцидентов.
- Каждая заявленная функция отмечена как реализованная, экспериментальная или запланированная.

## Открытые решения

До реализации собственного forge нужно отдельно согласовать:
- модель размещения и бюджет;
- требования к приватным и публичным репозиториям;
- подход к федерации и идентификации;
- юридические условия, лицензии и правила товарного знака;
- использование существующей forge-платформы вместо разработки с нуля.
