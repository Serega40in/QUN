# QUN Engineering Guide
Версия 0.1 · Основной репозиторий: https://github.com/Serega40in/QUN

## Перед началом
1. Открой текущую ветку, последние коммиты и связанные Issues/PR.
2. Найди модуль, README, тесты, workflow и конфигурацию.
3. Определи зависимости изменения: продукты, API, таблицы и клиенты.
4. Для auth, RLS, платежей/кошелька, секретов, обновлений и распределённого хранения сначала оцени риски и план проверки.
5. Соблюдай ограничения пользователя по веткам. Если нельзя работать напрямую в main, используй feature branch и pull request.

## Принципы
- Предпочитай небольшие изменения с проверяемой целью.
- Сохраняй API и форматы данных, если изменение контракта не согласовано.
- Не отключай RLS, авторизацию, валидацию или тесты ради обхода ошибки.
- Не помещай секреты в код, документацию, HTML, workflow-логи или коммиты.
- Для UI проверяй мобильный экран, пустые состояния, ошибки, загрузку, доступность и навигацию.
- Для БД документируй миграции, индексы, ограничения, RLS и обратную совместимость.
- Храни версии промптов для генеративных функций и проверяй соответствие продукту.

## Проверки перед словом «готово»
По возможности выполни линтер/статический анализ, unit и integration tests, сборку, мобильную проверку, проверку workflow и опубликованного URL, проверку безопасности и секретов. Приводи только фактически выполненные проверки. Если инструменты не позволяют запускать код, укажи это явно.

## Git workflow
- Для существенных изменений используй отдельную ветку и pull request.
- Перед записью проверь существование файла и его текущую версию.
- Не затирай несвязанные изменения.
- Обновляй документацию, статус и manifest при необходимости.
- PR не означает автоматический merge или deployment.
