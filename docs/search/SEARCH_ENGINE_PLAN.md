# QUN Search — план перехода к полноценному веб-поиску

Статус: проектирование MVP; существующий `/search/` — каталог разделов QUN, не веб-поисковик.

## Цель
Создать поисковую систему с собственным индексом, crawler, API выдачи и прозрачным ранжированием. Не выдавать каталог сервисов или ИИ-ответы за результаты поиска по всему интернету.

## Этап 1 — рабочий Web Search MVP
- Сохранить текущий статический интерфейс `search/index.html`.
- Добавить серверный endpoint `/api/search?q=...` через Cloudflare Worker.
- В качестве временного источника веб-результатов подключить поставщика поискового API с ключом, хранящимся только в Worker secrets.
- Нормализовать результаты в общий формат: title, url, snippet, source, published_at (если доступно).
- Показывать источник результатов и честно обозначать, что выдача пока приходит от внешнего провайдера.
- Сохранить отдельный режим поиска по разделам QUN; не смешивать его с веб-выдачей без явной маркировки.
- Добавить лимиты запросов, валидацию параметров, тайм-ауты, безопасное отображение текста и базовую защиту от злоупотреблений.

## Этап 2 — собственный индекс
- Очередь URL и состояние обхода: queued, fetched, indexed, skipped, failed.
- Crawler с ограничением частоты запросов на домен, соблюдением robots.txt, запретом обхода приватных IP/localhost, лимитами размера и времени ответа.
- Извлечение canonical URL, title, description, основного текста, языка, даты и исходящих ссылок.
- Дедупликация URL и содержимого, повторное индексирование по расписанию, обработка удалённых страниц.
- Начать с разрешённых открытых сайтов и доменов QUN; расширять покрытие постепенно.
- Не обходить авторизованные, paywall- или иные закрытые страницы без разрешения.

## Этап 3 — индекс и ранжирование
- Для раннего прототипа: PostgreSQL full-text search; далее оценить Meilisearch/OpenSearch по цене, масштабу и эксплуатационной нагрузке.
- Базовый BM25/полнотекстовый скоринг, язык, свежесть и качество документа.
- Позже — ссылочные сигналы и семантический retrieval; защита от SEO-спама и манипуляций.
- Проводить оценку на наборах запросов и релевантных результатов, а не менять ранжирование только по интуиции.

## Рекомендуемая архитектура
- Frontend: существующий GitHub Pages `/search/`.
- API: Cloudflare Worker (секреты не помещать в клиентский JavaScript).
- Метаданные и очередь на раннем этапе: существующий Supabase/Postgres, если доступен и подходит по лимитам.
- Поисковый индекс: PostgreSQL FTS для прототипа; отдельный движок при росте.
- Crawler/индексатор: отдельный Worker или фоновый исполнитель с очередью и контролем частоты.
- QUN Node/Compute можно подключать позже для разрешённых распределённых задач, но не считать их уже настроенными.

## Ограничения и критерии готовности
- Нельзя обещать «весь интернет»: покрытие зависит от обхода, доступности сайтов, robots.txt, ограничений и ресурсов.
- Не хранить ключи провайдера в GitHub Pages или публичном репозитории.
- Не запускать массовый crawler без доменных лимитов, защиты SSRF и мониторинга.
- MVP готов, когда реальный пользовательский запрос проходит через UI → API → источник данных, выдаёт настоящие результаты со ссылками, обрабатывает пустой запрос/ошибки/лимиты и имеет тесты.
- Собственный поиск считается отдельным следующим этапом, пока страницы не обходятся и не индексируются собственным crawler.

## Следующие практические шаги
1. Выбрать доступного провайдера веб-поиска и проверить актуальные условия бесплатного тарифа/API.
2. Создать Worker endpoint и хранить ключ только в secrets.
3. Подключить UI к endpoint, показывать loading/error/empty states и источник результатов.
4. После проверки реального end-to-end поиска начать индексатор и собственную выдачу.
