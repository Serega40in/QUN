# QUN NFT Marketplace — MVP

Статус: проектирование. Это целевая архитектура, а не уже работающая торговая площадка.

## Продуктовая идея
QUN Gallery / QUN Collectibles — галерея цифрового искусства и NFT в единой эстетике QUN. Начинать с просмотра, профилей создателей, коллекций и прозрачных карточек произведений; торговлю подключать только после проверки смарт-контрактов и безопасного сценария кошелька.

Рабочие названия: **QUN Gallery** для художественной галереи, **QUN Market** как более широкий маркетплейс экосистемы. Не утверждать, что названия или домены свободны, пока это не проверено.

## Этапы
### MVP 0 — каталог без финансовых операций
- Главная страница и тематические подборки.
- Страница коллекции, карточка NFT, история и описание.
- Страница автора/создателя.
- Поиск, фильтры, избранное.
- Прозрачный статус: концепт, опубликовано on-chain, снято с продажи.
- Ссылки на исходную работу, контракт и внешний рынок, если они проверены.
- Панель модерации и механизм жалоб на нарушение авторских прав.

### MVP 1 — кошелёк и подтверждённое владение
- Подключение совместимого кошелька через стандартный провайдер.
- Только публичный адрес и чтение данных; никогда не хранить seed-фразы.
- Чтение коллекций/токенов из выбранной сети.
- Проверка сети, контракта и метаданных.
- Ясные сообщения о комиссиях и транзакциях.
- Подписи только для конкретной понятной операции, которую пользователь сам инициировал.

### MVP 2 — торговля
- Выбрать: интеграция с проверенным внешним рынком или собственные контракты/торговый протокол.
- Не принимать средства на централизованный баланс на первом этапе.
- Перед запуском — независимый аудит контрактов, тестнет, тестирование повторного воспроизведения, ошибок округления, re-entrancy и прав доступа.
- Показывать цену, валюту, сетевые комиссии, комиссию площадки и условия авторского вознаграждения до подтверждения.
- Отдельно проектировать отмену листинга, споры, фишинговую защиту и поддержку.

### MVP 3 — QUN ID и расширение экосистемы
- Связать профиль QUN ID с публичным адресом только по добровольной криптографической подписи.
- Не публиковать приватные персональные данные в блокчейне.
- Возможная интеграция с QUN Wallet/Coin — только после отдельной спецификации и проверки правовых рисков.
- Не выпускать собственный токен исключительно ради маркетплейса.

## Предлагаемая техническая архитектура
- Frontend: адаптивный web app в визуальном языке QUN.
- Backend/API: каталог, поисковый индекс, отчёты о нарушениях, модерация и кэш публичных блокчейн-данных.
- Database: PostgreSQL/Supabase для профилей, подборок, избранного и состояния индексатора; on-chain владение не считать истинным только по записи в БД.
- Media storage: объектное хранилище с резервированием; для NFT-медиа — устойчивые адреса и проверка целостности.
- Blockchain adapter: отдельный слой для чтения выбранной сети и контрактов; не привязывать интерфейс к одной сети без причины.
- Indexer: синхронизация событий, повторная обработка, сверка с сетью и мониторинг отставания.
- Security: rate limits, журнал действий модерации, секреты только на сервере, проверки загружаемых файлов, CSP и защита от XSS.

## Базовая модель данных
- creators: id, display_name, bio, avatar_uri, verified_status.
- collections: id, creator_id, name, description, chain_id, contract_address, license_uri, status.
- assets: id, collection_id, token_id, title, description, media_uri, metadata_uri, attributes_json, content_hash.
- listings: id, asset_id, seller_address, price, currency, status, expires_at, external_order_uri.
- favorites: user_id, asset_id.
- reports: id, reporter_id, target_uri, reason, status, moderator_notes.
- chain_events: chain_id, tx_hash, log_index, block_number, event_type, payload_json.
Для production потребуется уникальность chain_id + contract_address + token_id, индексация, миграции и правила доступа.

## UX-принципы
- Премиальная галерея, не перегруженная финансовыми графиками.
- Чётко отличать концепт-арт от существующего NFT.
- Всегда показывать сеть и адрес контракта с возможностью копирования.
- Не рисовать фальшивые объёмы, рейтинги, владельцев или «верификацию».
- В мобильном интерфейсе главные действия доступны большим пальцем.
- Кнопки покупки/подключения кошелька не показывать как активные, пока действие не реализовано.

## Критерии готовности MVP 0
- [ ] Адаптивная главная и каталог.
- [ ] Рабочие страницы коллекций и отдельных объектов.
- [ ] Поиск/фильтры и состояния загрузки/ошибки/пустого каталога.
- [ ] Авторство, лицензия и статус объекта видны.
- [ ] Жалоба на контент работает.
- [ ] Все ссылки проверены, нет фиктивных данных, если они не помечены как демонстрационные.
- [ ] Документация развёртывания и резервного копирования.
- [ ] Пройдены проверки доступности, безопасности и производительности.

## Решения, которые нельзя выдумывать заранее
До разработки торговых функций нужно определить сеть, модель хранения, комиссии, юрисдикции, модерационную политику и требования к авторским правам. До этого можно создавать дизайн, каталог и тестовые данные, но нельзя заявлять, что реальная торговля доступна.
