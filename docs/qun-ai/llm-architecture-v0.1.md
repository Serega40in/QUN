# QUN LLM v0.1 — архитектура, хранение и безопасное развитие

**Статус:** engineering proposal + first implementation steps. Не является заявлением о готовой собственной foundation-модели.  
**Дата:** 2026-11-13  
**Репозиторий:** https://github.com/Serega40in/QUN

## Цель

QUN LLM — семейство моделей и адаптеров для QUN AI. QUN AI — продуктовый помощник экосистемы; QUN LLM — модельный слой; QUN Memory — retrieval и пользовательский контекст; QUN Training — проверяемый процесс улучшения моделей. Эти понятия нельзя смешивать.

## Принцип запуска

1. **Desktop / local-first:** QUN Desktop Agent обращается к Ollama на `127.0.0.1:11434`. Первая проверенная базовая модель — `qwen2.5:0.5b`; она подходит для smoke-тестов и простых задач, но не считается качественной финальной моделью QUN.
2. **Web / shared runtime:** сайт GitHub Pages не может обращаться к localhost пользователя. Веб-клиент обращается только к защищённому QUN AI Gateway (сейчас Supabase Edge Function `qun-ai-chat`). Для собственной модели Gateway использует настраиваемый OpenAI-compatible endpoint. До настройки удалённого inference endpoint сайт продолжает работать через текущий Gemini-провайдер.
3. **Compute:** QUN Compute — место для opt-in GPU worker или отдельного inference service. Сначала один контролируемый endpoint; распределённый inference не внедрять до измерения качества, задержки и стоимости.
4. **Control plane:** QUN Core сохраняет роль управления устройствами и заданиями. Не создавать параллельную сеть, вторую очередь или отдельный identity layer.
5. **Fallback:** если QUN LLM endpoint недоступен, Gateway сообщает об ошибке или использует только явно настроенный fallback. Не скрывать переключение провайдера и не заявлять, что ответ сгенерирован QUN LLM, если это не так.

## Где хранить

- **Model weights и tokenizer:** локальный каталог Ollama для desktop; для серверной модели — приватный каталог/том на GPU-хосте или объектное хранилище артефактов с checksum и лицензией. Не помещать веса в PostgreSQL.
- **Model registry:** метаданные модели (идентификатор, базовая модель, версия, quantization, checksum, лицензия, benchmark, дата, источник сборки) в GitHub manifest на этапе MVP; позже — таблица/registry в QUN Core/Supabase. Не хранить секреты в manifest.
- **Training data:** отдельный приватный dataset store, версионированные JSONL-файлы и manifest; пользовательские разговоры по умолчанию не являются обучающими данными.
- **Conversation history:** только в существующей защищённой схеме QUN AI с проверкой RLS/владения. Не передавать приватные диалоги volunteer nodes.
- **User memory:** отдельный слой retrieval с прозрачным управлением и удалением; это не изменение весов модели. Секреты, seed-фразы, пароли и особо чувствительные данные не индексировать.
- **Artifacts/backups:** QUN Storage — целевой слой, но пока не считать его production-готовым. До этого — private storage, encryption at rest, access control, retention и проверка восстановления.

## Как QUN LLM будет «обучаться»

Не обновлять веса автоматически после каждого сообщения. Использовать управляемый цикл:
1. пользователь явно отправляет feedback или команда проекта утверждает пример;
2. удаляем идентификаторы и секреты, проверяем права на данные и лицензию;
3. собираем отдельный версионированный dataset (JSONL) с происхождением и согласием;
4. запускаем evaluation против фиксированного набора QUN вопросов и adversarial/safety тестов;
5. при наличии совместимого GPU обучаем LoRA/QLoRA-адаптер на выбранной базовой модели;
6. сравниваем baseline и candidate на точности, выдуманных ссылках, приватности, latency и русском языке;
7. человек утверждает выпуск; храним версию, checksum, датасет и результаты тестов, сохраняем rollback.
Пользовательские диалоги не используются для обучения по умолчанию. Fine-tuning не гарантирует знания новых фактов; актуальные факты лучше подключать через RAG по проверенной базе знаний.

## RAG / база знаний QUN

Начальный корпус — публичные и утверждённые документы `docs/qun-ai/knowledge/`. Сначала реализовать индексацию с метаданными источника, commit/revision, дату проверки и URL. При ответе возвращать только найденные фрагменты с источниками; при отсутствии подтверждения сообщать об этом. Векторные embeddings/pgvector добавлять после проверки доступности расширения и RLS в текущем Supabase-проекте. Не делать public read на личные conversation rows.

## Предлагаемые модельные версии

- **QUN LLM Local 0.1:** текущая `qwen2.5:0.5b` в Ollama для проверки интеграции, не для публичного качества.
- **QUN LLM Instruct 0.1:** после выбора лицензии и benchmark — более сильная instruct-модель, которую можно обслуживать на бесплатном GPU runtime при доступности, либо на локальном GPU. Для публичного сайта нужен постоянно доступный endpoint; бесплатные notebooks обычно не гарантируют uptime.
- **QUN LLM QUN-adapter 0.1:** будущий LoRA-адаптер на проверенных QUN knowledge/instruction examples. Не называть модель обученной, пока training run, evaluation и artifact не проверены.

## Security / privacy

- API keys и service-role keys хранятся только в Supabase secrets/secret manager или защищённом local credential store.
- Не делать browser-to-model direct calls с секретами.
- Endpoint URL и модель настраиваются только оператором сервиса; не принимать произвольный upstream URL из пользовательского запроса.
- Установить auth/rate limits, ограничение размера истории/запроса, timeout, safe error handling и минимальные журналы без полного текста личных запросов.
- Для внешнего inference явно документировать, какой провайдер обрабатывает запрос. Не отправлять private chats на сторонний endpoint без законного основания и информирования.
- Model weights лицензируются отдельно от кода QUN. Проверять лицензию base model и датасетов до публикации.

## Порядок реализации

1. Подключить конфигурируемый OpenAI-compatible provider в `qun-ai-chat`, сохранив текущий Gemini fallback.
2. Проверить локальный Desktop Agent end-to-end с Ollama.
3. Настроить один доступный QUN Compute inference endpoint и секреты вне GitHub.
4. Подключить QUN AI web через Gateway; добавить статус активного провайдера без раскрытия секретов.
5. Создать evaluation set и RAG ingestion для утверждённых документов QUN.
6. Добавить feedback dataset pipeline с явным согласием и ручной модерацией.
7. Только после измерений выбрать базовую модель и запускать LoRA/QLoRA.
8. После smoke/security tests открыть PR и выпустить отдельно; не выкатывать непроверенный runtime в production автоматически.

## Definition of done для v0.1

- Desktop chat работает через локальную модель без внешнего API.
- Gateway может вызвать настроенный OpenAI-compatible endpoint и корректно ограничивает запрос.
- Без QUN endpoint существующий Gemini path продолжает работать.
- В логах нет API keys и полного текста пользовательских запросов.
- Есть benchmark, provenance, license и checksum для каждого model artifact.
- Ни один пользовательский диалог не попадает в training set без явного разрешения.
- Веб-интерфейс не показывает статус «QUN LLM online» до успешного health check.
