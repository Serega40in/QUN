# QUN Node 0.1 + QUN Storage 0.1 — спецификация MVP
**Версия:** 0.1 · **Дата:** 12 октября 2026 года  
**Статус:** проектирование / ближайшая цель разработки, не production-сервис.

## Цель
Проверить основу распределённого хранения на искусственных данных и нескольких независимых узлах прежде, чем подключать реальные сервисы QUN. Существующие Messenger, Auth и QUN AI не отключать и не мигрировать на этом этапе.

## Принципы
- Local-first: узел может работать локально без внешнего координатора.
- Только тестовые данные: никакой пользовательской переписки, credentials, дампов БД, секретов и приватных ключей.
- Проверяемость: SHA-256, манифесты, события и повторяемые тесты.
- Ограничение ресурсов: максимальный объём, размер объекта, число задач и сетевой трафик задаются конфигурацией.
- Минимальные привилегии: не запускать переданный пользователем код и не открывать публичные порты по умолчанию.
- Восстановление: при потере одной тестовой реплики данные можно восстановить из оставшейся подтверждённой копии.
- Никаких обещаний о 100% доступности или полностью бесплатной эксплуатации.

## Node 0.1
1. Конфигурация узла: идентификатор, каталог хранения, лимит диска, тестовый режим.
2. Health endpoint: версия, состояние процесса, свободное место и время последней проверки; без секретов.
3. Локальное хранилище объектов.
4. Журнал событий с ротацией и без приватного содержимого.
5. Команды проверки целостности и безопасного завершения.
6. Unit-тесты и тест запуска/перезапуска.

## Storage 0.1
1. Приём синтетического тестового объекта.
2. Вычисление SHA-256 до сохранения.
3. Сохранение объекта с безопасным именем, не основанным на произвольном пути клиента.
4. Манифест: object ID, хеш, размер, версия формата, идентификатор тестового узла и время.
5. Повторное чтение и проверка хеша.
6. Сравнение манифеста с содержимым и обнаружение повреждения.
7. Копирование на независимый тестовый узел.
8. Восстановление из проверенной копии и повторная проверка хеша.

## Минимальные сценарии приёмки
- Узел запускается и сообщает health.
- Тестовый объект сохраняется и читается без изменения хеша.
- Изменение байта приводит к провалу проверки целостности.
- При наличии двух реплик и отключении одного узла объект читается со второго.
- Повреждённая реплика выявляется, восстановленная копия совпадает с исходным SHA-256.
- Перезапуск процесса не теряет манифесты тестовых объектов.
- Превышение квоты безопасно отклоняется.
- В логах и HTTP-ответах нет секретов и полного содержимого объектов.

## Следующие этапы
1. Прототип локального узла и хранилища.
2. Тестовый процесс с двумя/тремя независимыми экземплярами.
3. Имитация отказов и автоматическое восстановление.
4. Обзор угроз, ключей, шифрования и метрик RPO/RTO.
5. Только после оценки безопасности — интеграционный дизайн для сервисов QUN.

## Пока не делать
- Не хранить реальные личные сообщения на добровольческих узлах.
- Не запускать произвольный код на чужих компьютерах.
- Не делать блокчейн обязательным условием хранения.
- Не переносить Auth/базу действующего Messenger до проверенного плана миграции и восстановления.
- Не считать Guardian источником правды о состоянии узлов, пока нет реального API.
