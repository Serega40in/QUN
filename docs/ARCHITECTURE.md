# QUN — архитектура экосистемы и правила изменений

Редакция: 1.0 · 20 октября 2026

## Неприкосновенное правило

**Не заменять и не переписывать главную страницу QUN при добавлении нового продукта.** Перед любыми изменениями сначала читать текущие исходники, историю и этот документ. Делать минимальные адресные изменения. Сохранять работающие ссылки, функции, поиск и интеграции. Не удалять/переносить действующий сервис без отдельного явного решения владельца.

## Информационная архитектура

- `/` — главный портал экосистемы: бренд, заметный поиск QUN Search, быстрые переходы к продуктам, каталог/категории и статусы. Не лендинг одного продукта.
- `/search/` — отдельный интерфейс QUN Search; поиск доступен также с главной.
- `/messenger/` — отдельный сервис QUN Messenger; никогда не подменять его поиском. До создания или миграции папки нельзя придумывать новый URL: найти действующий адрес в репозитории/документации.
- `/ai/` — QUN AI.
- `/social/` — QUN Social.
- `/publisher/` — QUN Publisher.
- `/market/` — QUN Market.
- `/wallet/` — QUN Wallet.
- `/node/` и связанные страницы хранения — QUN Node / QUN Storage.
- `/core/` — документация и прототип собственного блокчейна QUN Core.
- `/guardian/` — административная панель QUN Guardian; приватные функции должны быть защищены авторизацией.
- `/brandbook/` — брендбук, журнал и презентационные материалы.
- `/docs/` — архитектура, инструкции, решения и техническая документация.

Пути выше являются целевой логикой, а не подтверждением, что все страницы уже существуют. Для каждого сервиса использовать существующий проверенный URL, пока миграция отдельно не согласована.

## Принципы интерфейса

1. Главная — навигационный центр, а не копия каталога одного приложения.
2. Поиск QUN — заметный центральный элемент; должен вести в самостоятельный QUN Search и передавать поисковый запрос, если это поддерживается.
3. Messenger и Search — разные продукты и разные ссылки.
4. Каталог продуктов строится из единого реестра `config/products.json`, где для каждого элемента есть `id`, название, путь, категория, статус и описание. Не дублировать продуктовые URL в десятках страниц.
5. Общие цвета и компоненты едины, но каждый продукт может иметь собственный интерфейс.
6. Mobile-first, быстрый запуск, доступность с клавиатуры и понятные состояния ошибок.
7. Ясно различать работающий продукт, прототип, разработку, план и замороженное направление. Не заявлять о работающих функциях без проверки.
8. Все существующие проекты и возможности сохраняются; новые продукты добавляются как записи каталога и отдельные страницы.

## Правила работы с GitHub

Перед изменением:
- найти актуальную главную и связанные страницы;
- прочитать текущую версию и историю коммитов;
- определить, что пользователь просил изменить, и не затрагивать остальное;
- проверить ссылки, идентификаторы, поиск, маршруты и мобильный интерфейс.

После изменения:
- проверить diff/содержимое и внутренние ссылки;
- выполнить доступные тесты;
- проверить GitHub Actions и опубликованные страницы;
- сообщить, что действительно проверено, а что ещё нет.

Запрещено:
- заменять `index.html` целиком «для красоты» без прямого согласования;
- подменять существующие продукты друг другом;
- выдумывать адреса приложений;
- считать commit равным успешной публикации;
- объявлять PDF типографски готовым без проверки технических требований.

## QUN Core

QUN Core задуман как собственный блокчейн QUN. Не заменять его токеном в другой сети. Текущий локальный код — ранний прототип, не mainnet. До реальных активов необходимы подписи, корректное состояние, nonce, защита от двойной траты, сетевой протокол, консенсус, тестовая сеть и независимый аудит.

## Изменение архитектуры

Изменение этого документа или целевых URL должно сопровождаться объяснением причины и явным согласованием. При конфликте между этой архитектурой и уже работающим маршрутом сохранять текущий маршрут до проверенной миграции.
