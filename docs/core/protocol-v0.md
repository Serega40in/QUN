# QUN Core — протокол локального прототипа v0

> Статус: инженерная спецификация текущего прототипа, не утверждённый консенсус-протокол. Не использовать для реальных средств.

Этот документ описывает поведение, которое уже видно в коде `core/`. Он фиксирует текущие соглашения, чтобы следующий этап P2P и консенсуса не строился на неявных предположениях.

## 1. Состав прототипа

- Язык узла: Rust; HTTP API построен на Axum.
- Сеть: локальная разработка, по умолчанию `127.0.0.1:8787`.
- Состояние: JSON-снимок цепочки и ledger на диске.
- Подписи: Ed25519.
- Хеш блоков: SHA-256 от сериализованного JSON-кортежа фиксированного порядка.
- Консенсус, peer-to-peer, mempool, синхронизация между узлами и выбор канонической ветки пока не реализованы.

## 2. Транзакция

Текущие поля транзакции:

| Поле | Тип | Правило |
| --- | --- | --- |
| `from` | string | hex-представление публичного Ed25519-ключа для подписанного пути |
| `to` | string | непустой адрес получателя |
| `amount` | u64 | больше нуля |
| `nonce` | u64 | следующий nonce отправителя, начиная с 1 |

Подписанный объект содержит `transaction`, `public_key` и `signature`. Публичный ключ и подпись передаются как lowercase hex; ключ имеет 32 байта, подпись — 64 байта.

Подписываемый payload — UTF-8 JSON от кортежа в точном порядке:

```json
["QUN_TX_V1","<from>","<to>",<amount>,<nonce>]
```

Подпись Ed25519 проверяется по байтам этого JSON. Адрес отправителя должен совпадать с hex публичного ключа. Это формат текущего кода, а не окончательная межъязыковая wire-spec: перед подключением независимых реализаций следует заменить неформализованную JSON-сериализацию на строго определённое бинарное или каноническое представление и закрепить тест-векторами.

## 3. Блок и хеширование

Genesis-блок имеет индекс и timestamp 0, предыдущую ссылку `QUN_GENESIS_V1`, пустые списки транзакций и хеш, вычисленный legacy-форматом.

Для обычного демонстрационного блока хеш вычисляется как:

```text
SHA256(UTF8(JSON([index, timestamp, previous_hash, transactions])))
```

Для блока с подписанными транзакциями:

```text
SHA256(UTF8(JSON([
  "QUN_BLOCK_V2",
  index,
  timestamp,
  previous_hash,
  transactions,
  signed_transactions
])))
```

Проверка цепочки сейчас проверяет genesis, последовательность индексов, ссылку на предыдущий хеш, соответствие транзакций подписанным объектам, подписи и хеш каждого блока. Это проверка целостности, но не доказательство консенсуса или единственности истории.

## 4. Правила ledger

- Нельзя переводить ноль, делать перевод самому себе или использовать пустые адреса.
- Баланс отправителя должен покрывать сумму.
- Получатель не должен переполнять `u64`.
- Nonce отправителя должен быть ровно предыдущий nonce + 1.
- При ошибке узел применяет транзакции к копии состояния и не сохраняет частичный результат.
- `/dev/fund` — отдельный локальный механизм тестового пополнения, не блокчейн-эмиссия и не часть консенсуса.

Важно: начальные балансы из `/dev/fund` сохраняются в снимке состояния отдельно от истории блоков. Поэтому текущий JSON-снимок нельзя считать полностью воспроизводимым из genesis и блоков. До devnet нужно спроектировать детерминированную эмиссию/генезис и восстановление состояния исключительно из проверяемой истории.

## 5. Локальный HTTP API

| Метод и путь | Назначение |
| --- | --- |
| `GET /health` | состояние процесса и предупреждение о режиме разработки |
| `GET /chain` | текущая цепочка |
| `GET /blocks/:index` | один блок по индексу |
| `GET /accounts` | балансы и nonce локального ledger |
| `POST /dev/mine-signed` | проверить подписи и ledger, записать подписанный блок |
| `POST /dev/mine` | legacy-демо-путь без криптографической аутентификации отправителя |
| `POST /dev/fund` | тестовое пополнение; выключено, если не задано `QUN_ENABLE_DEV_FUNDING=true` |

API не имеет аутентификации и должен оставаться на localhost. Не выставлять его напрямую в интернет.

## 6. Обязательные условия до публичного testnet

1. Зафиксировать версионированную каноническую сериализацию и независимые тест-векторы.
2. Определить genesis, эмиссию, комиссии (если нужны), точную модель аккаунта и правила перехода состояния.
3. Сделать восстановление состояния детерминированным из проверяемой истории; исключить доверие к произвольному JSON-ledger.
4. Спроектировать mempool, лимиты и правила сортировки транзакций.
5. Реализовать P2P с аутентификацией сообщений, ограничением ресурсов и безопасной синхронизацией.
6. Выбрать и формально описать консенсус, финальность, fork-choice и защиту от двойной траты.
7. Добавить property/fuzz-тесты, тесты несовместимых версий, сетевые тесты и независимый аудит.
8. Провести threat-model review; только после этого решать вопрос о публичном testnet.

## 7. Терминология статуса

- **Локальный прототип** — текущий статус: можно запускать один узел и проверять подписанные транзакции.
- **Devnet** — несколько независимых узлов обмениваются данными и достигают согласованного состояния по явно описанным правилам.
- **Testnet** — публично доступная тестовая сеть с описанным консенсусом, мониторингом, операционными процедурами и ограничениями.
- **Mainnet** — отдельный запуск после аудита, устойчивой эксплуатации и осознанного решения о реальных активах.

Ни наличие Explorer, ни успешные unit/CI-тесты сами по себе не означают, что QUN Core является распределённой сетью или готов к реальным средствам.
