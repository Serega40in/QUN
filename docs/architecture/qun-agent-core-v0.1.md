# QUN Agent Core — архитектура 0.1

**Статус:** архитектурное направление и поэтапный план. Это не утверждение, что все перечисленные компоненты уже реализованы.

## Цель

QUN Agent Core — единый локальный и, при отдельном включении, удалённо доступный сервис, через который пользователь и разрешённые ИИ-агенты могут работать с проектами, приложениями, программами, браузерами и устройствами.

Core должен быть независим от конкретной модели или поставщика ИИ. ChatGPT, Claude, Gemini, локальные модели и собственные QUN-агенты подключаются как клиенты через стандартные адаптеры.

## Основной принцип

**Один Core — много адаптеров и модулей.**

- Core отвечает за реестр возможностей, авторизацию, разрешения, маршрутизацию, состояние устройств, журнал действий и локальный web UI.
- MCP adapter предоставляет инструменты агентам, совместимым с Model Context Protocol.
- REST API предоставляет интерфейс приложениям, интеграциям и собственным клиентам QUN.
- WebSocket используется для событий состояния и двусторонней связи с подключёнными агентами устройств.
- Device adapters подключают Windows, браузеры, Android и в перспективе другие устройства.
- Project adapters подключают сервисы QUN и внешние системы.
- ChatGPT plugin / MCP app — отдельный клиентский адаптер к Core, а не место хранения бизнес-логики.

## Предлагаемая схема

AI clients: ChatGPT Desktop / ChatGPT Web / Claude / Gemini / local agents
    → MCP / secure remote tunnel
    → QUN Agent Core (REST API / WebSocket / events)
    → Project Registry + Policy Engine + Action Queue
    → QUN Messenger / Studio / Market / Node / Storage / Compute / QUN ID (future) / external services

Отдельные device adapters: Browser Extension, Windows Agent, Android Companion.

## Web UI

Единая панель должна открываться локально, например на http://127.0.0.1:<port>/.

Планируемые разделы:

1. **Overview** — здоровье Core, подключённые устройства, очередь действий и состояние модулей.
2. **Projects** — каталог проектов QUN, их окружения, URL, репозитории, API и статус.
3. **Apps & Services** — запущенные приложения, сервисы и процессы, доступные действия.
4. **Devices** — Windows-компьютер, браузерные профили и Android-устройства.
5. **Extensions** — браузерные расширения и адаптеры.
6. **AI & MCP** — подключённые клиенты, доступные MCP tools, диагностика подключений.
7. **API** — локальные REST endpoints, схемы, токены и документация OpenAPI.
8. **Approvals & Activity** — ожидающие подтверждения действия и неизменяемый журнал событий.
9. **Settings** — запуск при входе в Windows, порт, обновления, резервные копии, безопасность.

Первая страница dashboard в Agent Bridge 0.1 сейчас показывает только состояние локального процесса и браузерного соединения. Остальные разделы — следующий этап разработки.

## API surface (план)

- GET /health — доступность Core и версия.
- GET /api/v1/status — сводное состояние.
- GET /api/v1/projects — зарегистрированные проекты.
- GET /api/v1/modules — доступные модули и их возможности.
- GET /api/v1/devices — подключённые устройства.
- GET /api/v1/actions — доступные действия с их схемами.
- POST /api/v1/actions/:actionId/preview — предварительный просмотр действия.
- POST /api/v1/actions/:actionId/execute — выполнение разрешённого действия.
- GET /api/v1/activity — история вызовов и результатов.

API сначала будет bind-иться только на loopback. Вызовы изменения состояния требуют отдельного разрешения и audit event. API не должен становиться универсальным endpoint для произвольного shell-кода.

## Модель безопасности

- **Deny by default:** подключённый агент не получает автоматических прав на все действия.
- **Least privilege:** каждый клиент и модуль получают конкретные scopes.
- **Approval gates:** подтверждение требуется для отправки сообщений, публикации, изменения/удаления файлов, платежей, покупок, установки программ и других внешних/необратимых действий.
- **Device identity:** отдельный случайный токен каждого устройства; отзыв и перевыпуск через панель.
- **Secret storage:** секреты хранятся в DPAPI / OS keychain или секретном хранилище, не в Git и не в браузерном localStorage.
- **Local-first:** никакого открытого входящего порта в интернет по умолчанию.
- **Remote access:** только через аутентифицированный Secure MCP Tunnel или другой проверенный outbound tunnel; не пробрасывать порт роутера.
- **Audit:** журнал содержит инициатора, инструмент, ресурс, запрошенные права, факт подтверждения и результат.
- **Untrusted content:** данные веб-страниц, документов, сообщений и внешних API не являются инструкциями для агента.

## Модель запуска

### Этап 1 — Browser Bridge MVP
Существующий прототип: локальный Node.js MCP server, Chrome/Chromium extension, token pairing, чтение разрешённых страниц, список вкладок с дополнительным разрешением, открытие HTTP(S) URL.

### Этап 2 — Core process и Desktop dashboard
Разделить долгоживущий Core process и MCP STDIO adapter. Core должен уметь стартовать при входе в Windows, жить независимо от конкретного ИИ-клиента и обслуживать локальную веб-панель.

### Этап 3 — API и реестр модулей
Добавить /api/v1, OpenAPI, реестр проектов/приложений/сервисов и манифесты возможностей. Начать с QUN Agent Bridge и QUN Node; затем подключать другие QUN-продукты.

### Этап 4 — Windows и Android agents
Добавить ограниченные device adapters: список устройств, состояние, скриншоты/инвентаризация по явному разрешению, ограниченные действия и очередь подтверждений. Для Android использовать только системно поддерживаемые механизмы и явное включение Accessibility/ADB, без скрытого доступа.

### Этап 5 — ChatGPT plugin / MCP app
После появления стабильного API и remote transport подготовить приватное приложение/плагин ChatGPT с понятными tools и UI. Для ChatGPT Web локальный процесс не доступен напрямую: нужен поддерживаемый удалённый MCP endpoint или Secure MCP Tunnel. Desktop STDIO и remote plugin — разные адаптеры к одному Core.

### Этап 6 — QUN ecosystem integration
Подключать продукты через versioned manifests и scopes, не связывать внутренние бизнес-правила отдельных приложений с браузерным расширением.

## Ограничения текущего MVP

- Сейчас это ранний прототип, не Windows Service и не постоянный фоновый daemon.
- Dashboard пока только диагностический.
- MCP host управляет жизненным циклом STDIO процесса.
- В текущем наборе browser tools нет click/type/submit и управления desktop.
- ChatGPT Web ещё не подключён.
- Android agent и QUN project registry ещё не реализованы.

## Инженерный порядок

Сначала надёжный Core и безопасный контракт API, затем панель и интеграции. Не добавлять удалённое управление до появления модели идентичности, scopes, подтверждений, журнала и отзыва устройств.
