**Статус:** локальный тестовый прототип. Не production и не публичная распределённая сеть.

## Что реализовано
- локальный HTTP API, по умолчанию слушающий только 127.0.0.1;
- локальная веб-панель состояния узла на `/` и `/dashboard`;
- endpoint состояния узла GET /health;
- сохранение тестовых UTF-8 объектов и JSON-манифестов;
- SHA-256 проверка содержимого;
- endpoint проверки целостности;
- ограничение размера запроса/объекта и проверка ID против path traversal;
- тесты записи, чтения, обнаружения повреждения и квоты;
- периодическая сверка настроенных peers, повторная отправка объектов после возвращения узла и восстановление повреждённой копии по проверенной SHA-256;
- ранний установочный сценарий Windows (PowerShell + Node.js LTS/Git через winget) и запуск на Android через Termux;
- отказ от незашифрованного HTTP для удалённых peers, чтобы не передавать общий секрет репликации открытым текстом;
- управляемая регистрация узла через одноразовый код на управляющем сервере Supabase; сервер выдаёт UUID и индивидуальный 256-битный секрет узла, на устройстве хранится локальная копия, а в базе — SHA-256 секрета;
- heartbeat раз в 30 секунд и серверный статус online/stale/offline; узел считается online при heartbeat не старше 90 секунд;
- локальный endpoint POST /enroll принимает код только от официальной веб-панели QUN Node и сохраняет учётные данные регистрации в каталоге данных с правами доступа владельца;
- health-статус показывает регистрацию и последний heartbeat; публичная автоматическая регистрация и вознаграждения выключены;
- веб-панель на GitHub Pages может прочитать только безопасный статус локального агента после явного нажатия пользователя; CORS разрешён только для origin https://serega40in.github.io;
- Windows desktop shell запускает локальный агент и открывает панель внутри приложения;
- отдельный Android APK содержит foreground-службу и экран мониторинга батареи, времени работы и локального состояния. Это пока мобильная основа агента, не полноценный узел распределённого хранилища.

## Требования
Node.js 20 или новее. Зависимости npm не нужны.

## Запуск
Из каталога services/qun-node:

```bash
npm test
npm start
```

По умолчанию панель управления и API доступны только локально на http://127.0.0.1:8787/ (панель также доступна по /dashboard). Для регистрации откройте веб-панель QUN Node на GitHub Pages, введите одноразовый код и имя устройства; секрет узла не отображается в браузере. Данные сохраняются в ./.qun-node-data. Не публикуйте этот порт в интернет.

Переменные окружения:
- QUN_NODE_HOST — по умолчанию 127.0.0.1; не меняйте на 0.0.0.0 для тестов с реальными данными.
- QUN_NODE_PORT — по умолчанию 8787.
- QUN_NODE_DATA_DIR — каталог хранения.
- QUN_NODE_ID — отображаемый ID локального узла.
- QUN_NODE_PEERS — список URL тестовых узлов через запятую, например http://127.0.0.1:8788.
- QUN_NODE_REGISTRY_URL — URL управляющего сервиса регистрации (по умолчанию настроен на тестовый проект QUN).
- QUN_NODE_REGISTRY_KEY — публичный Supabase publishable key (по умолчанию настроен для тестового проекта QUN).
- QUN_NODE_SHARED_TOKEN — общий секрет для репликации, не короче 32 символов; задай одинаковое значение на тестовых узлах. Не коммить его в GitHub и не используй в публичной сети. Для удалённых peers используй HTTPS; HTTP допускается только для loopback-адресов в локальных тестах.

## Примеры запросов

Проверить состояние:

```bash
curl http://127.0.0.1:8787/health
```

Создать синтетический объект:

```bash
curl -X POST http://127.0.0.1:8787/objects \
  -H "Content-Type: application/json" \
  -d '{"id":"demo-001","data":"QUN synthetic test object"}'
```

Прочитать объект:

```bash
curl http://127.0.0.1:8787/objects/demo-001
```

Проверить целостность:

```bash
curl http://127.0.0.1:8787/objects/demo-001/verify
```

Получить манифест:

```bash
curl http://127.0.0.1:8787/objects/demo-001/manifest
```

## Репликация между тестовыми узлами
Узел может отправлять сохранённые тестовые объекты на адреса из QUN_NODE_PEERS через защищённый внутренний endpoint. На принимающем узле должен быть задан тот же QUN_NODE_SHARED_TOKEN. После POST /objects ответ показывает успешные/неуспешные реплики. Репликация при записи дополнена периодической сверкой примерно каждые 5 секунд (интервал настраивается через `QUN_NODE_RECONCILE_INTERVAL_MS`). Узел повторно пытается связаться с недоступными peers; после возвращения узла синхронизирует отсутствующие объекты, а повреждённую копию восстанавливает из проверенного экземпляра. Состояние последней сверки видно в `GET /health` в поле `reconciliation`. Если две корректные копии одного ID содержат разные хеши, данные автоматически не перезаписываются — фиксируется конфликт. Это экспериментальный механизм для тестовой сети, не консенсус и не production repair-протокол.

Для проверки можно запустить два экземпляра в отдельных терминалах с разными портами и каталогами. На принимающем узле: QUN_NODE_PORT=8788, QUN_NODE_DATA_DIR=./.qun-node-b, QUN_NODE_ID=node-b и QUN_NODE_SHARED_TOKEN=ваша_случайная_строка_не_короче_32_символов. На отправляющем: QUN_NODE_PORT=8787, QUN_NODE_DATA_DIR=./.qun-node-a, QUN_NODE_ID=node-a, QUN_NODE_PEERS=http://127.0.0.1:8788 и тот же QUN_NODE_SHARED_TOKEN. На Windows PowerShell переменные окружения задаются через $env:NAME='value'. Сначала запусти принимающий узел, затем отправляющий.

## Важные ограничения
- Нет поиска данных на других узлах при чтении, нет шифрования объектов на диске, нет защищённой регистрации публичных узлов, репутации/anti-Sybil механизмов или расчёта вознаграждений. Текущая периодическая сверка работает только с явно настроенными peers и требует доверенного общего секрета.
- Основной API не содержит пользовательской аутентификации, поэтому слушает только loopback. Не выставлять в публичную сеть. Внутренние endpoint-ы репликации требуют Bearer-секрет.
- Тестировать только искусственные данные, без сообщений, паролей, пользовательских данных, дампов базы и ключей.
- Манифест и объект сохраняются отдельно; атомарность всей пары при внезапном отключении питания ещё требует усиления.
- Автотест репликации проверяет два отдельных процесса, отказ внутренних endpoint-ов без секрета, восстановление после отключения peer, исправление повреждённого объекта и повреждённого манифеста. Следующий шаг — расширить fault-injection, проверить несколько peers и добавить безопасную регистрацию узлов без общего публичного секрета.
- Не считать QUN Guardian live-панелью до подключения реального защищённого API.
