# QUN Node 0.1 + QUN Storage 0.1

**Статус:** локальный тестовый прототип. Не production и не публичная распределённая сеть.

## Что реализовано
- локальный HTTP API, по умолчанию слушающий только 127.0.0.1;
- endpoint состояния узла GET /health;
- сохранение тестовых UTF-8 объектов и JSON-манифестов;
- SHA-256 проверка содержимого;
- endpoint проверки целостности;
- ограничение размера запроса/объекта и проверка ID против path traversal;
- тесты записи, чтения, обнаружения повреждения и квоты.

## Требования
Node.js 20 или новее. Зависимости npm не нужны.

## Запуск
Из каталога services/qun-node:

```bash
npm test
npm start
```

По умолчанию API доступен только локально на http://127.0.0.1:8787. Данные сохраняются в ./.qun-node-data. Не публикуйте этот порт в интернет.

Переменные окружения:
- QUN_NODE_HOST — по умолчанию 127.0.0.1; не меняйте на 0.0.0.0 для тестов с реальными данными.
- QUN_NODE_PORT — по умолчанию 8787.
- QUN_NODE_DATA_DIR — каталог хранения.
- QUN_NODE_ID — отображаемый ID локального узла.
- QUN_NODE_PEERS — список URL тестовых узлов через запятую, например http://127.0.0.1:8788.
- QUN_NODE_SHARED_TOKEN — общий секрет для репликации, не короче 32 символов; задай одинаковое значение на тестовых узлах. Не коммить его в GitHub и не используй в публичной сети.

## Примеры запросов

Проверить состояние:

```bash
curl http://127.0.0.1:8787/health
```

Создать синтетический объект:

```bash
curl -X POST http://127.0.0.1:8787/objects \
  -H "Content-Type: application/json" \
  -d '{"id":"demo-001","data":"QUN synthetic test object"}'
```

Прочитать объект:

```bash
curl http://127.0.0.1:8787/objects/demo-001
```

Проверить целостность:

```bash
curl http://127.0.0.1:8787/objects/demo-001/verify
```

Получить манифест:

```bash
curl http://127.0.0.1:8787/objects/demo-001/manifest
```

## Репликация между тестовыми узлами
Узел может отправлять сохранённые тестовые объекты на адреса из QUN_NODE_PEERS через защищённый внутренний endpoint. На принимающем узле должен быть задан тот же QUN_NODE_SHARED_TOKEN. После POST /objects ответ показывает успешные/неуспешные реплики. Это начальная синхронная репликация, не консенсус и не полноценный repair-протокол.

Для проверки можно запустить два экземпляра в отдельных терминалах с разными портами и каталогами. На принимающем узле: QUN_NODE_PORT=8788, QUN_NODE_DATA_DIR=./.qun-node-b, QUN_NODE_ID=node-b и QUN_NODE_SHARED_TOKEN=<случайный секрет длиной не менее 32 символов>. На отправляющем: QUN_NODE_PORT=8787, QUN_NODE_DATA_DIR=./.qun-node-a, QUN_NODE_ID=node-a, QUN_NODE_PEERS=http://127.0.0.1:8788 и тот же QUN_NODE_SHARED_TOKEN. На Windows PowerShell переменные окружения задаются через $env:NAME='value'. Сначала запусти принимающий узел, затем отправляющий.

## Важные ограничения
- Это начальная репликация тестовых объектов; нет автоматического repair после позднейшего повреждения/отключения узла, нет поиска данных на других узлах при чтении и нет шифрования объектов на диске.
- API не содержит аутентификации, поэтому слушает только loopback. Не выставлять в публичную сеть.
- Тестировать только искусственные данные, без сообщений, паролей, пользовательских данных, дампов базы и ключей.
- Манифест и объект сохраняются отдельно; атомарность всей пары при внезапном отключении питания ещё требует усиления.
- Следующий шаг — отдельный replication/repair протокол для двух локально поднятых экземпляров и fault-injection тесты.
- Не считать QUN Guardian live-панелью до подключения реального защищённого API.
