# Участие в разработке QUN

Добро пожаловать! QUN строится как открытая экосистема: вы можете улучшать ядро, создавать независимые продукты на базе QUN, тестировать приложения и помогать с документацией.

- **Developer Hub:** https://serega40in.github.io/QUN/developers/
- **Основной репозиторий:** https://github.com/Serega40in/QUN
- **Сообщество:** https://t.me/quncommunity
- **Новости проекта:** https://t.me/qunnews

## Выберите свой путь

1. **Core Contributor** — исправления и развитие общего кода QUN.
2. **Ecosystem Builder** — независимые приложения, игры, боты, SDK и интеграции на базе документированных интерфейсов QUN.
3. **Community Contributor** — тестирование, документация, переводы, дизайн и отчёты об ошибках.

Свой продукт не требуется передавать QUN. Для включения в официальный каталог в будущем потребуется описать продукт, его лицензию, совместимость и контакт поддержки.

## Первый вклад: пошагово

1. Найдите задачу с меткой `good first issue` или `help wanted`. Если подходящей задачи нет, откройте Issue и сначала согласуйте направление.
2. Сделайте Fork репозитория `Serega40in/QUN`.
3. Создайте отдельную ветку от актуального `main`, например `fix/node-retry`, `docs/api-quickstart` или `feature/sdk-example`.
4. Внесите небольшой, сфокусированный набор изменений.
5. Запустите доступные тесты и проверки. В описании PR укажите команды и результат.
6. Откройте Pull Request в ветку `main` исходного репозитория.
7. Ответьте на замечания ревью и обновите ветку при необходимости. Не сливайте собственный PR самостоятельно.

Пример команд:

```bash
git clone https://github.com/<YOUR-USERNAME>/QUN.git
cd QUN
git remote add upstream https://github.com/Serega40in/QUN.git
git fetch upstream
git switch -c docs/my-first-contribution upstream/main
# внесите изменения
git diff --check
git status
git add <files>
git commit -m "docs: explain a QUN workflow"
git push -u origin docs/my-first-contribution
```

Затем откройте PR из вашей ветки в `Serega40in/QUN:main`. Перед началом работы синхронизируйте fork с upstream, если он устарел.

## Требования к Pull Request

- Один PR — одна логическая задача.
- Опишите проблему, предлагаемое решение и альтернативы, если они существенны.
- Перечислите изменённые компоненты, тесты и известные ограничения.
- Не включайте секреты, токены, приватные ключи, реальные пользовательские данные, сборки и случайные файлы.
- Не меняйте публичные API, сетевые протоколы, схему данных или формат хранения без обсуждения совместимости.
- Для изменений поведения добавляйте тесты, если это практически возможно.
- Не утверждайте, что функция готова, если она не проверена.
- Не запускайте и не добавляйте в CI недоверенный код с production-секретами.

## Проверки и принятие изменений

CI помогает проверить стиль diff и наличие базовых файлов проекта. Успешный CI не означает автоматического принятия изменения. Сопровождающий оценивает корректность, безопасность, тесты, совместимость и соответствие направлению QUN.

Обычно нужен как минимум один одобрительный отзыв сопровождающего, не являющегося автором изменения. Для критичных компонентов могут потребоваться дополнительные профильные проверки. Правила защиты ветки GitHub настраиваются отдельно в настройках репозитория; этот документ сам по себе их не включает.

## Изменения критической инфраструктуры

Для QUN Node, Storage, Compute, идентификации, авторизации, криптографии, кошелька, сетевого протокола и финансовых операций:

- сначала откройте Issue или Design Proposal;
- опишите модель угроз и сценарии отказа;
- добавьте негативные тесты и проверки совместимости;
- не включайте удалённое выполнение произвольного кода;
- не считайте локальные тесты доказательством безопасности или готовности публичной сети;
- не публикуйте уязвимости публично до согласования безопасного раскрытия через [SECURITY.md](SECURITY.md).

## Архитектурные предложения

Крупные изменения обсуждаются заранее в Issue. Фиксируйте принятые решения в документации, чтобы будущие участники могли понять причины выбора. Не создавайте скрытые зависимости от личных серверов, секретов или недокументированных API.

## Лицензии и права

Перед отправкой кода убедитесь, что вы вправе его предоставлять. Не копируйте код, изображения, тексты или зависимости с несовместимыми условиями. До утверждения лицензии основного репозитория не предполагайте, что весь код QUN разрешено использовать, изменять и распространять на любых условиях. Уточняйте лицензионные вопросы в Issue.

## Взаимодействие

Будьте уважительны, предметны и открыты к обратной связи. Следуйте [Кодексу поведения](CODE_OF_CONDUCT.md). Участие добровольное; принятие вклада, сроки и вознаграждение не гарантируются, если иное не согласовано письменно.

Спасибо, что помогаете делать QUN надёжнее и полезнее.
